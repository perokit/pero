# Pero CLI and service lifecycle

## User experience

The intended installation and daily control surface is one globally installed npm executable:

```sh
npm install -g @perokit/pero
pero run
pero status
pero agents ls
pero stop
```

The package is `@perokit/pero`, published under the `perokit` npm organization from [github.com/perokit/pero](https://github.com/perokit/pero). The unscoped `pero` package name is already taken, so Pero ships as a public scoped package while keeping the terminal command `pero`. npm [scopes](https://docs.npmjs.com/about-scopes/) allow the same package suffix in a separate namespace, and the [`bin` field](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#bin) chooses the executable name independently:

```json
{
  "name": "@perokit/pero",
  "repository": { "type": "git", "url": "git+https://github.com/perokit/pero.git" },
  "bin": { "pero": "./bin/pero.js" }
}
```

Ship compiled JavaScript and publish `@perokit/pero` with `npm publish --access public`. Users need a supported Node.js/npm installation, but do not need to clone the repository, compile TypeScript, install PostgreSQL or Redis, or start a container.

## Command contract

| Command | Expected behavior |
|---|---|
| `pero run` | Ensure one background Pero process is running for the selected data directory. On first use, create local directories and guide the owner through missing setup. Return only after startup and readiness succeed. Repeated calls report the existing process. |
| `pero run --foreground` | Run the same daemon attached to the terminal for debugging or an external service manager. |
| `pero stop` | Ask the running daemon to stop intake, cancel or finish active work within a bounded period, close the database, and exit. Report when it is already stopped. A Workflow Run stopped mid-way is recorded `interrupted` on the next start, and retried there if its Workflow allows another attempt. |
| `pero status` | Show process state, version, data directory, health, and whether Telegram and each configured Agent Runtime are available. Exit with status 3 when Pero is stopped. |
| `pero logs` | Show the most recent entries of `logs/pero.log` (`-n <count>`, default 50) as readable lines in local time; `--follow` streams new entries and `--json` prints the raw JSON lines. Reads files only, so it works whether or not the daemon is running; it points to `logs/daemon.out` rather than streaming it. |
| `pero settings show` | Show the installation settings by the names `set` takes; the Telegram bot token only as set or not set, and where it comes from. `pero settings` alone does the same. |
| `pero settings set <key> [value]` | Change one setting through the daemon: `default-provider`, `claude.model`, `claude.effort`, `codex.model`, `codex.effort`, `default-working-directory` (relative to the current folder, `~` allowed), `shared-instructions`, `main-agent` (the enabled Agent that General topics and direct chats onboarded from now on are assigned; existing Channels keep theirs; unset, `main` is used and created when needed), `history-carryover` (how many recent messages a replacing Session starts with; 0 turns it off), `default-permissions` (`ask` or `bypass`: how the tools of Agents created from now on are approved), `history-retention-days` (unset keeps all history; otherwise messages older than that many days are deleted within the hour, every hour, and when Pero starts; runs and Notifications keep their text), `timezone`, `max-concurrent-runs`, or `telegram-bot-token`. Without a value it prompts on a terminal or reads stdin, so long instructions can come from a file. The token is refused as an argument, so it never lands in shell history. |
| `pero settings unset <key>` | Clear a setting: provider options return to the provider default, shared instructions to none, and the stored bot token is deleted. The default working directory can be changed but not cleared. |
| `pero backup <file>` | Ask the running daemon to write a backup: a consistent snapshot of the database from the SQLite online backup API, archived with `secrets/` and a manifest as an owner-only gzip tar. The database includes each Channel's message history. Logs, `run/`, and working folders are not included. The file must be outside the data directory; an existing file is replaced. |
| `pero restore <file>` | Restore a backup into the selected data directory, which must be missing or empty; it never overwrites an installation. Runs without the daemon and refuses while one answers for that directory. Warns about each working folder recorded in settings or on an Agent that does not exist here. [Operating Pero](./OPERATIONS.md#moving-to-a-fresh-machine) describes a restore on a fresh machine, with the working folders and provider conversations restored from the owner's own backup. |
| `pero agents ls` | List saved Agents, including provider, model, effort, working directory (and whether it follows the default), permissions, and enabled state; the main Agent is marked. `pero agents` alone does the same. |
| `pero agents show <name>` | Show an Agent's settings and the Channels assigned to it, with what each Channel's next turn does: resume its Session, or start a fresh one because the provider or effective folder changed (and whether it starts with the Channel's recent messages). Warns when its folder is missing or not accessible. |
| `pero agents create <name>` | Create an Agent; what is not given comes from the installation settings. Options: `--title`, `--provider claude\|codex`, `--model`, `--effort`, `--working-directory <folder>` (relative to the current folder, `~` allowed; without one it follows the default working directory), `--instructions <text>` (`-` reads stdin), `--no-shared-instructions`, `--permissions ask\|bypass`, and `--skip-git-repo-check` (lets a Codex Agent work outside a Git repository). |
| `pero agents edit <name>` | Change an Agent with the same options; each `--no-…` form (`--no-title`, `--no-model`, `--no-effort`, `--no-instructions`, `--shared-instructions`, `--no-skip-git-repo-check`) returns a setting to its default, and `--follow-default` makes it follow the default working directory again. A new provider or effective folder makes its next turn in each Channel start a fresh Session that carries over the Channel's recent messages; model, effort, and instructions apply from the next turn of the same Session. Agents created by onboarding are edited the same way; the name cannot change. |
| `pero agents disable <name>` / `enable <name>` | Stop an Agent from answering, keeping its Channels and Sessions, or let it answer again; enabling checks that its folder exists and is accessible. |
| `pero channels ls` | List Channels by ID with their address (for Telegram, `<chat_id>` or `<chat_id>:<topic_id>`), topic or chat title, assigned Agent, and enabled state. `pero channels` alone does the same. Channels are created by onboarding, not by hand. |
| `pero channels show <channel>` | Show a Channel by its ID: its Agent, what its next turn does with its Session, and how much history it holds. |
| `pero channels assign <channel> <agent>` | Point a Channel at another enabled Agent, such as a new topic at an existing Agent instead of the one onboarding made. Its Session is closed, so the Agent's next turn there starts a fresh one that carries over the Channel's recent messages. |
| `pero channels disable <channel>` / `enable <channel>` | Ignore a Channel's messages, keeping its Agent and Sessions, or let it reach its Agent again. A disabled Channel is not onboarded again. |
| `pero channels history <channel>` | Print the Channel's latest messages (`-n <count>`, default 20, at most 500) in local time, with direction (`in` or `out`) and origin (`user`, the Agent, `pero` for Pero's own notices, or `workflow` and its name for a delivered Notification). |
| `pero telegram chats` | List allowed chats (kind, title, whether topics are on, whether the bot is an administrator) and chats that recently asked to pair, with their IDs. |
| `pero telegram allow <chat-id>` | Allow a group or direct chat. A group's ID is negative (`-100…`); a direct chat's ID is the owner's user ID. Both appear in the pairing hint the bot sends to a chat it does not serve yet. |
| `pero telegram deny <chat-id>` | Remove a chat from the allowlist. Its Channels and Agents stay and resume if it is allowed again. |
| `pero workflows ls` | List Workflows by name with their Agent, how many Triggers they have, and enabled state. `pero workflows` alone does the same. |
| `pero workflows show <name>` | Show a Workflow's Agent, input, and Triggers, each with its schedule and next run, and the Channels it notifies. Warns when its Agent is disabled. |
| `pero workflows create <name>` | Create a Workflow: `--agent <name>` (an enabled Agent) and `--input <text>` (what each run sends it; `-` reads stdin) are required, `--title` is optional. `--max-attempts <n>` (1 to 10, default 1) is how many times a run may start in all: a run Pero stopped before it finished is recorded `interrupted` on the next start and, while its attempts allow, queued again as a new run; the default never starts it again, since its Agent may already have changed files. A Workflow runs only once a Trigger starts it. With `--history`, each run also reads Channel history: a transcript (local time, Channel title, who spoke, and text) goes in place of `{{history}}` in the input, or after it when there is none. By default it holds what people wrote in every Channel since the previous successful run (the last 24 hours for the first run), so each message is read once and a retry reads the same messages as the run it retries. `--history-channels <ids|all>` reads only those Channels (IDs as `pero channels ls` lists them, separated by commas), `--history-messages people|all` adds the Agents' replies with `all`, `--history-hours <n>` (1 to 720) reads the last n hours before each run instead, and `--history-since-last-run` goes back to the default. Any of these turns history on. A transcript over its budget keeps the newest messages and says how many it left out. A run whose window has no messages completes without its Agent, unless `--run-when-empty` is given (`--no-run-when-empty` undoes it). Pero's own notices are never included. |
| `pero workflows edit <name>` | Change a Workflow with the same options; `--no-title` clears the title. History options change only what they name, starting from the defaults when the Workflow read no history, and `--no-history` stops runs reading it. A new Agent must be enabled. The name cannot change. |
| `pero workflows disable <name>` / `enable <name>` | Stop a Workflow's Triggers from starting it, keeping them, or let them start it again. Workflows are never deleted, since their runs refer to them. |
| `pero workflows run <name>` | Run a Workflow now through its manual Trigger (`pero triggers add <name> --manual`), which must be enabled, like the Workflow and its Agent. The run waits for a free slot (`max-concurrent-runs`) and for the Workflow's previous run to finish, then prints the Agent's answer, or that it was skipped because its history window had no messages; a failed run exits with status 1 and prints why. `--no-wait` prints the run's ID and returns. A run starts a provider conversation of its own, never a Channel's Session, and adds nothing to Channel history; nobody is there to approve tools, so an Agent with `ask` permissions is refused any tool that would need approval. |
| `pero workflows notify <name> <channel>` | Notify a Channel, by its ID as `pero channels ls` lists it, of each run of the Workflow that finishes from then on: a completed run's answer, headed by the Workflow's title (or name), or why a run failed or was interrupted without a retry. Cancelled runs and runs skipped for an empty history window notify no one. A disabled Channel can be notified. Notifications are delivered within seconds and retried for about a day while the Channel can't be reached; one to a chat that is no longer allowed fails. `--remove` stops it; the Notifications already made are kept. Saying it twice changes nothing and says so. |
| `pero runs ls` | List the latest Workflow Runs, newest first (`-n <count>`, default 20, at most 500), with Workflow, status, attempt, what started them (`manual`, `schedule`, or `retry of run <id>`), and when they were created and finished. `--workflow <name>` and `--status <status>` narrow it. `pero runs` alone does the same. |
| `pero runs show <run>` | Show a run: status, attempt, what started it, its times, the run that retries it, the Channel history it read (how many messages, from which Channels, and how many the budget left out), the Agent's answer or why it failed, and each Notification it left with its delivery status, attempts, and last error. A failed, interrupted, or cancelled run that is not retried yet says how to retry it. |
| `pero runs retry <run>` | Queue a failed, interrupted, or cancelled run again as a new run keyed `retry:<run>` with the next attempt, then print the Agent's answer as `pero workflows run` does (`--no-wait` returns at once). The owner decides, so the Workflow's `--max-attempts` does not limit it, but the Workflow and its Agent must be enabled. The retry reads the same Channel history window and is claimed before the Workflow's other waiting runs; when a run completed since has read some of those messages too, the command notes it. A run has one retry: retrying it again names that retry instead, and a run that completed or has not finished is refused. |
| `pero runs cancel <run>` | Cancel a Workflow Run by ID: one waiting to start is `cancelled` at once and never starts; a running one has its Agent's turn aborted, and the command returns once it is recorded `cancelled`. A run that has finished cannot be cancelled. |
| `pero notifications ls` | List the latest Notifications, newest first (`-n <count>`, default 20, at most 500), with their run, Workflow, Channel, status (`pending`, `delivered`, or `failed`), attempts out of ten, next attempt, and last error. `--status`, `--workflow <name>`, `--channel <id>`, and `--run <id>` narrow it. `pero notifications` alone does the same. |
| `pero notifications show <notification>` | Show a Notification: its Channel, status, attempts, next attempt, last error, delivered message ID, and the message itself, then what stands in the way of delivery: a chat that is no longer allowed, or Telegram not being ready as `pero status` reports it. |
| `pero notifications retry <notification>` | Make a waiting Notification due now, or give a failed one ten fresh attempts starting now, then wait up to 30 seconds for the attempt and say whether it was delivered; a failed attempt exits with status 1 and says why and when Pero tries again. `--no-wait` returns at once. A delivered Notification is refused, since it would be sent twice. It creates no Workflow Run. |
| `pero triggers ls [workflow]` | List Triggers by ID, or one Workflow's, with their schedule, next run, and enabled state. `pero triggers` alone does the same. |
| `pero triggers add <workflow>` | Start a Workflow on a schedule: `--cron "<expression>"` takes five fields (minute hour day month weekday, such as `"0 9 * * *"`) or `@hourly`, `@daily`, `@weekly`, `@monthly`, or `@yearly`; `--timezone <zone>` is the IANA time zone it follows, by default the `timezone` setting at the time it is added. `--manual` adds instead the Trigger for runs started by hand; a Workflow has at most one. A schedule prints its next run and is refused when no date ever matches it (such as `"0 9 30 2 *"`). |
| `pero triggers remove <trigger>` | Remove a Trigger by ID. The runs it started are kept. |
| `pero triggers disable <trigger>` / `enable <trigger>` | Stop a Trigger from starting its Workflow, keeping it, or let it start it again. An enabled schedule runs next at its first time from then, so times it was disabled are not caught up. |

Every command except `run`, `run --foreground`, `stop`, `status`, `logs`, and `restore` requires the running daemon. When it is stopped, the command exits with `Pero isn't running — start it with pero run` and does not start it implicitly.

The same CLI will expose settings, Agent, Channel, Workflow, and Trigger management commands. Start with list/show/create/edit/disable operations; each sends a request to the daemon, whose application services validate references and apply the change. For example, creating an Agent should accept a provider, optional provider options (model, effort), and optional working directory, with the SQLite installation defaults used when omitted; an Agent without its own folder follows the default working directory. A change of provider or effective folder makes that Agent's next turn in each Channel start a fresh Session; model, effort, and instructions apply from the next turn of the same Session (see the [Session policy](./ARCHITECTURE.md#5-runtime-contract)). Export/import commands can provide reviewable JSON for people who want to edit definitions as files; SQLite remains authoritative after import.

## First run and local files

Pero works on a workspace: `--workspace`/`-w`, then `PERO_WORKSPACE`, then the nearest folder holding `.pero/` from the current folder upward (the home folder itself never counts), then `~/workspace` when it holds `.pero/`. Its state lives in the workspace's `.pero/`. Without a workspace, the legacy data directory is `~/.pero`, overridable with the `--data-dir` option or the `PERO_HOME` environment variable; an explicit option or variable always wins over a workspace found from the current folder. On a first `pero run`, the daemon initializes the SQLite database, applies migrations, seeds installation defaults, and reports ready without Telegram or provider setup. An interactive `pero run` then guides the owner through choosing the working folder all Agents share (prefilled with the current folder, or `~/workspace` when run from the home directory), Telegram setup (the bot token, then pairing a chat, described below), and provider sign-in checks over the control endpoint, explaining the external Claude Code and Codex CLI sign-in commands when needed. A non-interactive run leaves the daemon running in a degraded state and prints the missing settings, each with the command that fixes it, rather than waiting for input; it does not guess a working folder. Every answer goes to the daemon at once, so an interrupted setup keeps what was done, and a later `pero run` asks only for what is still missing and checks sign-in again. A provider can be reported unavailable without silently changing billing mode or switching an Agent to another provider.

Only providers in use count toward health: the default provider and any provider an enabled Agent uses. The other one is still listed in `pero status`, marked `(not in use)`, and setup does not ask to sign in to it. The daemon runs `claude auth status` and `codex login status` as its own account when it starts and whenever `pero run` asks.

The Telegram bot token is stored in the workspace's `.env` as `PERO_TELEGRAM_BOT_TOKEN`, or in `secrets/telegram-bot-token` in a legacy data directory (owner-only, replaced atomically, and `.env` is added to the workspace's `.gitignore`), never in SQLite, logs, `pero status`, or `pero settings show`. A token in the daemon's environment as `PERO_TELEGRAM_BOT_TOKEN` wins over the stored one, which suits a service manager; `pero run` passes its own environment to the daemon it starts. Changing the token takes effect without a restart.

### Telegram setup

The recommended path gives each Agent its own topic in one private group:

1. Create a bot with [@BotFather](https://t.me/BotFather) and give Pero its token (`pero run` asks for it).
2. Create a group, turn on **Topics** in its settings, and add the bot as an administrator. No specific administrator right is needed; without administrator rights Telegram shows the bot only commands, mentions, and replies.
3. Allow the group. An interactive `pero run` waits for the bot to be added or messaged and offers to allow that chat; otherwise the bot answers the group with its chat ID, and `pero telegram allow <chat-id>` allows it. Turn on topics before allowing the group: that change gives the group a new chat ID. Pero follows the change if it happens later.
4. Create a topic per Agent. Pero creates an Agent named after the topic, with the installation defaults, and posts a welcome there; `pero agents edit` changes its instructions, provider, or folder. The General topic talks to the main Agent (`main` unless `main-agent` names another).

A direct chat with the bot works as well, alone or next to the group: message the bot and allow the user ID it replies with. It has no topics and talks to the main Agent, in a Session of its own.

```text
~/.pero/
├── pero.sqlite         # settings, definitions, runtime state, and message history
├── logs/
│   ├── pero.log         # daemon logs, JSON lines
│   └── daemon.out       # raw stdout/stderr of a daemon started by `pero run`
├── run/                 # local control endpoint and process metadata
└── secrets/             # owner-only local secrets when needed
```

Provider subscription credentials remain in the provider CLIs' own stores under the same OS account. The Telegram bot token is a separate secret: obtain it during setup or from the service environment and store it in owner-only local secret storage when persistence is needed. Never place provider credentials or Telegram tokens in Agent/Workflow rows or diagnostic output.

## Process and command boundaries

The npm executable is a thin command entry point: `bin/pero.js` loads the compiled [nest-commander](https://nest-commander.jhunt.dev/) CLI, which runs `CommandFactory.run(CliModule)`. `CliModule` imports only what commands need, not the full daemon `AppModule`, so commands start quickly without booting Telegram, the scheduler, or provider SDKs. `pero run` launches the NestJS daemon as a separate background process with logs redirected to local files, then waits for a readiness response. Node's [detached subprocess documentation](https://nodejs.org/docs/latest-v24.x/api/child_process.html#optionsdetached) describes the required detached/unreferenced process and disconnected standard I/O behavior. The daemon owns Telegram intake, scheduling, execution, notification delivery, and exclusive access to SQLite. A private local control endpoint serves lifecycle and management requests from the CLI; it must be accessible only to the owner account. The CLI never opens the database or loads TypeORM: it is a client of the control endpoint, sharing request schemas with the daemon. This keeps a single writer, lets the daemon update its in-memory state (schedules, Sessions, Channel routing) directly when definitions change, and ensures only the daemon runs migrations.

Once the database is open and migrated, the daemon must start and report ready even when settings are missing or invalid. A bad Telegram token, a signed-out provider CLI, or an invalid Agent folder marks that component degraded in `pero status` instead of failing startup, so the owner can always fix configuration with ordinary commands. Only file-level maintenance that requires a stopped daemon, such as restoring a backup, runs without it.

Permit only one daemon per data directory. Use an exclusive runtime lock and verify a live control endpoint before treating stored process metadata as current; a PID alone can be stale or reused. `pero stop` uses the control endpoint for graceful shutdown instead of killing whatever happens to have a saved PID. Database migrations happen before the daemon reports ready. `pero run` reports startup failures, printing the daemon's own output from `logs/daemon.out` and where to find the logs.

`pero run` keeps the process alive after the invoking terminal exits. Automatic startup after login or reboot is a separate service-manager feature, not implied by this command. The foreground mode provides a stable entry point for launchd, systemd, or another supervisor if the owner chooses one later. Upgrading the global npm package does not replace a running process; restart Pero to use the new version, with migrations run on startup.

## Packaging checks

The package must include the built CLI and daemon files, migrations, and runtime dependencies. Test installation from the packed npm artifact on supported operating systems and architectures, not only from a source checkout. [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3#installation) supplies prebuilt binaries for major platforms, but unsupported combinations may need a local build toolchain; make this a release check. Confirm that global installation creates a working `pero` command, first-run setup works under an ordinary user account, and `run`/`stop`/`status` work after a terminal closes. CI runs `scripts/check-packed-install.sh` on every supported OS and Node version: it installs the `npm pack` artifact into a temporary global prefix, loads `better-sqlite3` from it, and runs `run`, `status`, `backup`, `stop`, and `restore` from a fresh home directory.
